# 执行流程与状态机

## 1. 设计目标

所有模块从零实现，旧代码用于判断目标行为，不建立运行依赖。先以默认模式完成真实闭环，再接高级代理和定时。

一轮运行（run）包含本次全部 query、城市和平台展开的抓取任务；一个抓取 task 是一次 query × 城市 × 平台的 JobSpy 调用。保存运行快照后，每个抓取任务返回 DataFrame 即执行筛选、去重和入库，不等待整轮抓完。开启自动评分时，新岗位入库后进入独立评分队列，抓取后续任务与评分可以重叠；抓取任务不等待评分完成。已入库岗位立即可浏览，已排队显示 pending，关闭自动评分时显示 unscored。

## 2. 配置快照与任务

start 在短事务中保存无秘密的完整业务快照：启用方向/query 的稳定 ID、文本、城市/半径、Indeed 国家、平台、规则、rubric、模型协议/URL/ID/可选参数、运行参数、代理模式和 jobspy_commit（见 ARCHITECTURE）。秘密单独从运行时凭据读取。

检索任务按 query ID、城市稳定键、平台名排序展开，不使用方向显示顺序。每个任务独立 ID 与 stable_order；同一天多个 run 完全独立。没有启用 query、城市或平台时拒绝启动。默认不设任务/评分额度、不截取任务列表。

只有一个 pipeline 可运行；rescore 也通过同一运行互斥槽，忙时返回 BUSY，避免两个工作流同时覆盖评分。引导/测试使用全局 LLM 限速器，清理等待所有长操作完成。

运行中修改设置只影响下一轮。方向被删除时不影响已派发任务，但结果不得恢复被删标签。重命名只改变 UI 名称。

## 3. DataFrame 与按任务入库

每个 JobSpy 调用在独立工作进程执行，收集返回记录、错误、HTTP 指标和缺 JD 数量。普通模式按参数传递代理：off 明确直连，ordinary 两个平台都使用用户地址；mihomo 保持 LinkedIn 代理池、Indeed 独立直连的行为，并在设置帮助说明。

调用 JobSpy 使用 ARCHITECTURE 的固定提交和显式参数白名单：

- 每次明确传 site_name="linkedin" 或 "indeed"，不省略平台、不一次展开所有平台。
- 传 search_term、location、distance、results_wanted、hours_old；Indeed 另传 country_indeed，LinkedIn 不用该字段选择搜索国家。offset 固定为 0，不暴露分页恢复配置；hours_old=0 表示不限。
- LinkedIn 传 fetch_description=True，不再使用已弃用的 linkedin_fetch_description；description_format 显式为 markdown，保持 JD 处理约定。Indeed 使用搜索结果中的 JD，无需为统一接口而添加额外详情抓取。
- 不向 LinkedIn 传 is_remote/job_type 作为服务端筛选条件，该基线会忽略并警告；产品已配置的本地筛除规则保持独立。
- 未知参数不透传。捕获参数 ValueError/TypeError 并映射为 VALIDATION_ERROR，不进行网络重试。不要假设旧版 **kwargs 或内部类仍兼容。

JobSpy 返回后、任何 DataFrame 转换/拼接之前，读取 df.attrs.get("errors", {}) 与 df.attrs.get("warnings", {})，把当前平台的诊断随记录独立传回 service，不依赖 attrs 自动跨转换保留。errors 是平台到错误文本的映射，warnings 是平台到消息列表的映射；仅保存脱敏后的必要诊断。接口还可能直接抛异常，仍需单独捕获。

| 返回情况 | 任务处理 |
| --- | --- |
| 无平台错误，零行 | 成功零结果；空表也应有预期列 |
| 有平台错误，零行 | 失败，按有限策略重试 |
| 有平台错误，有记录 | 保留可用结果，执行有限重试；重试耗尽仍失败时提交部分结果并标记 failed |
| 仅有 warnings | 保存诊断，不单凭警告判失败或无限重试 |

少于目标不是失败。详情页失败可能只产生日志/warnings 和缺失 JD，不能仅用 errors 断言每条详情完整；单独统计缺 JD，按既定空记录/筛除规则处理，不伪造正文、不新增详情重抓子系统。正常空结果、网络失败与缺字段分别记录。

该提交不再使用旧 LinkedIn 会话的 HTTPAdapter Retry 配置。整任务有限重试和可打断退避由 App 负责，不能假设 JobSpy 已重试三次，也不额外叠加一套默认请求重试。HTTP 观测仍记录实际请求与 429；若未来引入请求级重试，必须与任务尝试分别计数。

直接在内存中处理 JobSpy 返回的 DataFrame，不导出再读取 JSON/CSV，不保存抓取结果文件、manifest、页码或 cursor 检查点。工作进程将结构化结果交给 service；service 串行完成数据库匹配和写入，工作进程不直接写业务库。网络调用在事务外。DataFrame 采用列名映射，不依赖旧列顺序或 dtype；NaN/NaT/pd.NA 转成业务空值，保留合法 0，日期和数值显式转换后再发给 service。使用标准 logging 收集工作进程日志并脱敏，禁止输出到协议 stdout，不依赖旧 JobSpy: 前缀。

同一次执行中，有限重试返回的部分结果在内存拼接，统一交给现有去重模块，不另建重试聚合系统。先按完整规范化记录字段精确去除重复返回行，保留首次出现顺序，再筛选及执行既定身份/内容去重；不同字段或身份的记录保留供业务规则判断。不生成哈希或摘要，错误与 warnings 独立收集。任务结束或重试耗尽后提交可用结果。岗位、身份/方向/来源关联、run_jobs、按自动评分开关创建的待评分任务、任务统计和最终任务状态在同一短事务提交；成功零结果同样提交任务完成状态。部分失败可提交可用岗位并将抓取任务标为 failed，后续仍可重跑。

成功任务必须表示结果已处理并提交，恢复时跳过；未提交或失败的抓取任务从头调用 JobSpy，不恢复分页。未入库的内存结果在崩溃后丢弃。任务统计保存本次聚合计数、重跑时替换该任务统计，不累加重试响应条数；本轮唯一岗位和新增数由 run_jobs 汇总，已有 is_new=true 不被后续命中改为 false。不实现结果重投递或返回原响应机制，已成功任务不再次提交；重试次数和诊断可累计。

## 4. 筛选与去重

过滤行为参考 [现有规则说明](../FILTERING-AND-DEDUP.md)，但实现为新模块、显式输入配置，不读取私人 YAML 或 rubric。

顺序：公司排除 → 空记录/明确兼职 → 启用的标题/资格/经验/方向规则 → ID → 直链 → 同轮跨平台公司标题 → 历史匹配 → 同轮公司/JD 内容比较。保留现有语义，不私自增加语义相似度。

每条记录只统计首个筛除原因。已命中的多方向来源要保留到最终合并，不把先返回的方向设为主方向。筛除后的完整记录不写业务库，处理后释放内存。

可配置规则用简单结构：enabled_rule_ids、经验阈值、公司名单、用户显式资格条件。经验阈值必须贯穿所有年数/替代分支判断，不只改一处常数。未知条件保留给评分，不能默认冲突。

私人 Summer 2027、个人语言能力和身份不能作为通用默认。返校冲突只有用户明确输入的毕业时间与岗位明确时间能判定时才启用；无法确认就保留。专业排除默认关闭。编写合成用例再实现，不搬运旧规则文件。

归一化要求保持现有行为：公司 NFKC/空白/casefold；直链去 utm 参数并排除通用招聘入口；JD Markdown/HTML 转文本、去展示差异后精确比较。不要额外跟随重定向或将不同文本做模糊合并。

锁定提交的 LinkedIn 实现不再填充 job_url_direct；直链为空时不生成 direct_url 身份，不以平台详情链接冒充外部直链。继续使用其他已有匹配规则，不修改去重条件，不补建外链抓取器；界面可打开 job_url，并保留其他来源后来提供的外链。参考：[LinkedIn 实现](https://github.com/speedyapply/JobSpy/blob/1988484ac76ff9ae57784750346842e967e8ba10/jobspy/linkedin/__init__.py)。

历史命中关联已有 job，不插入第二份 JD、不改首次发现时间、不覆盖原分。首次评分失败岗位的恢复由原 run 的评分任务负责，不能因新一轮历史命中就隐式重评。

以上规则逐批应用：身份和直链匹配覆盖库内身份；同轮跨平台公司标题与同轮内容比较包含当前 DataFrame 及 run_jobs 关联的本轮已入库岗位，不能把同轮规则扩展成全历史公司标题匹配。批内按返回记录顺序选择首个通过筛选的有效代表，移除方向/平台优先级；跨批次先入库者固定，不等待完整候选集合。后来的更完整 JD 或更优链接不替换代表正文/主字段，来源及其链接照常补充，不撤销或重做评分。并发返回顺序可能影响代表内容，不承诺与整轮集中处理的代表或合并结果完全一致；方向显示顺序不参与算法。续跑也不替换已提交实体。

## 5. 评分与恢复

开启自动评分时，新增 jobs 的 pending 状态与待评分任务在同一入库事务中登记，提交后才允许派发。抓取和评分使用独立并发限制，所有 LLM 入口仍共用全局并发/RPM；批量入库不绕过限速，评分积压保留在数据库，不阻塞后续抓取。

整个 run 用启动快照的 rubric/模型配置，输入固定为 title/company/description，不包含持续增加的来源或命中方向。本轮每个 job 对应一个评分任务，后续 query 命中同一岗位不重复登记。不同 job 即使输入相同也各自评分，不做输入缓存、在途共享、跨岗位结果复制或分发。任务使用稳定 job_id 关联，在 spec_json 保存必要参数，不依赖抓取文件。LLM 调用在线程池执行，service 内统一控制所有入口的并发/RPM，每次重试也重新经过限速调度。

成功立即事务提交到对应 jobs 并完成任务；失败写独立状态与简短错误，继续处理其他岗位。所有合格新岗位最终都被尝试，不按分数提前停止，不设收费数量上限。

用户手动评分：接收岗位发现或清单中勾选的 job_ids，或按 FilterSpec 在创建运行时解析出的岗位集合（之后入库的岗位不加入），按当前配置建立 kind=rescore 的运行，不改岗位主体和清单。开始后即使用户移出清单，在途结果仍可更新存在的 job；清理因运行互斥不会同时删除它。

停止/崩溃可在远端成功但本地未记录的窗口造成一次重发，普通 HTTP 无法承诺远端 exactly-once。必须保证已提交成功结果不重算；文档与 UI 不宣称任何情况下绝无重复费用。

运行快照包含 auto_score_enabled（默认 true）。为 false 时仍完成筛选去重入库，但新岗位为 unscored，不登记、派发评分任务；本文批次事务中的待评分任务仅在启用时创建。scoring 全部计数为 0，抓取及清理结束后按抓取结果结束运行，不因 unscored 岗位挂起。resume 使用原快照，不因当前设置变动补评。历史 unscored 岗位不因新运行命中或开关打开而自动送评。手动评分复用 rescore，绕过自动评分开关但遵守互斥和全局 LLM 限速。

## 6. 状态机

Run status：创建后直接 running → succeeded / partial / failed；用户停止 running → stopping → stopped；意外退出 → interrupted。stage 不持久化，由任务及当前操作推导，仅表示运行概况，为 retrieving/scoring/cleaning：仍有抓取待处理时为 retrieving（此时评分也可进行），抓取结束而评分仍在处理时为 scoring，最后为 cleaning。分别保存并展示抓取与评分的任务计数和活跃数，不用 stage 表达互斥的完整流水线。

- succeeded：所有计划抓取与评分成功，零结果也可成功。
- partial：有可用结果但仍有抓取/评分未完成。
- failed：启动失败或没有可用结果且执行失败。
- stopped/interrupted/partial/failed 可显式 resume；成功的 run 不可 resume，需 start 新 run。
- resume 只派发未完成任务：已提交成功的抓取任务跳过，其余从头重抓；已入库待评分岗位可以立即继续评分，不等待剩余抓取。每次显式 resume 给予新的有限尝试次数，累计尝试历史保留。抓取结束不等于 run 完成，须等所有可派发评分任务结束后确定 succeeded/partial/failed。
- Task status：pending/running/succeeded/failed/cancelled；恢复把未完成任务重新排队，成功任务保持。

正常停止立即停止抓取与 LLM 新请求派发及重试，取消尚未发出的线程池任务。抓取子进程最多等待 10 秒后终止；已发出的 LLM 请求等待成功或网络超时，成功评分照常提交。run 保持 stopping 并显示剩余在途请求数，全部结束后变为 stopped，期间不允许 start/resume/rescore。退避和 RPM 等待可打断，不把 requests 读取超时当作整个请求的总时限。未完成评分保留，续跑再派发。service 管理已启动的抓取子进程及 App 专用 Mihomo，正常退出时结束它们。

重连 UI 通过 app.status/runs.detail 恢复显示。关闭窗口不停止，隐藏 Dock 图标；菜单栏图标按本机偏好显示，二者都隐藏时仍照常调度。显式 Quit 时若有运行（含 stopping）先由 main 弹出确认，空闲直接退出。Electron main/service 驻留并继续定时调度；renderer 关闭不影响任务。显式 Quit 先正常停止，退出等待初值 10 秒，超时由 Electron 结束所持有的 Python service 及本 App 子进程，不等待线程池无限退出；再次启动按中断恢复。不要扫描旧 PID 自动杀进程，Mihomo 端口占用明确报错。App 自有 tmp/ 在进程停止后清理，失败记录日志，不保存文件清理恢复状态；抓取恢复不依赖原始文件。成功评分及时持久化，中断后只恢复未完成评分。

## 7. Mihomo 行为参考

全新代理模块实现下面已有策略，不能只做随机选节点的简化替代：

1. 从用户具体节点配置生成临时专用组和监听端口，不管理订阅，不修改用户原配置。
2. 候选打乱，排除其他端口占用/检测中的节点；每候选两次 HTTPS 延迟检查，再经该监听端口验证真实公网 IPv4。
3. 活动端口出口 IP 不重复；换下出口按配置冷却。检测失败恢复旧节点，候选次数有限。
4. 每端口一批结束、在途请求耗尽后才轮换，不切断另一端口任务。
5. 普通轮换失败可复检当前出口，通过后短暂等待再用；受到访问失败/429 压力的出口不能直接保留。
6. 压力时退避，轮换失败再退避重试一次，仍失败停用端口并归还未执行任务。
7. 记录简短统计，不输出节点凭据；所有端口不可用时保留部分结果并结束为未完成，不无限尝试。

HTTP 压力比率统计实际请求（包括底层已消化的 429），偶发已恢复错误不自动重跑成功 query。Mihomo 不可用不能静默切到直连。高级模式关闭代理池仍可调整其他参数。

## 8. 本地周期计划

Electron main 负责时钟/唤醒触发，service 负责 schedules、schedule_firings 幂等记账、单轮互斥和等待队列。最多 10 个计划，每个保存所选搜索、星期（空数组=只跑一次）、HH:mm、IANA 时区和开关；用时区库计算下一次时刻，不用固定 UTC offset。只跑一次的计划在该次触发记账后（无论开始、等待或未运行）自动关闭。

到点触发：空闲则立即开始运行（outcome=started）；已有运行则记 waiting，当前运行（含手动评分）结束后 service 按 scheduled_at 先后开始最早的 waiting，一次只开始一个。每个计划最多一个 waiting：再次到点时旧 waiting 改为 not_run（reason=waited_too_long），新触发继续等待。waiting 可取消（outcome=cancelled，不再显示）；用户停止当前运行不影响 waiting。service 启动时把残留 waiting 记为 not_run（reason=app_closed）。

不自动补跑。启动/唤醒时 main 为每个开启的计划计算自上次检查以来错过的时刻，只为最近一次记 not_run（reason=asleep 或 app_closed），并把同一计划之前未删除的 not_run 合并进 missed_count，不循环补跑或堆积多条。未运行由用户在界面手动 Run now 或删除；不为运行阻止系统休眠。修改计划从保存时刻向后计算，避免把新计划的过去时刻当错过任务。

运行按所选搜索生成任务：只取这些方向下启用的 query × 启用城市 × 启用平台，快照记录所选方向 ID（null=全部）及触发来源；去重、批次和统计仍按岗位全局计算，不因所选搜索不同而分库。

夏令时工程规则：不存在的本地时刻取当天跳时后的第一个有效时刻；重复时刻只触发第一次。schedule_id + scheduled_at 唯一约束阻止定时器重复触发。App 完全退出期间不调度，重新打开只按上面的规则记录未运行。
